# 新契约优化与验证记录

本轮按用户授权直接改变 KeyValue 输出契约，不保留每批全量兼容开关。
使用 complexity-optimizer 的“先确认契约、补边界测试、再测量”流程；数据顺序和持久性
不因接口迁移而弱化。前两轮报告是历史记录，本轮状态以本文和 ADR 0006 为准。

## 实现

- KeyValue 主输出切换五个控制列的增量协议；flush/stop 不重复发完整状态。
  删除无生产引用的旧全量轮询订阅器、字段剥离适配器和相应的旧模式测试。
  已有键常态更新不再为了输出构造完整 Arrow 快照。生产者实例身份来自初始 SHM 分配身份，
  不使用会在重启后重复的局部 segment_id。
- `KeyValueState` 按列维护状态，校验序号、版本、实例、批次边界，限制半批缓存。
  `StateSubscription` 处理 ready 屏障、快照加载期间的缓存和缺口失败。
  `select()` 允许 O(K log N) 的按键访问；完整快照明确按需生成。
- 原生 append 经 TableActor 提交 Parquet 与 manifest；后台检查点默认每秒运行，周期可配置。
  每次先捕获完整写入前缀并封存、提交 WAL，归档回执，再提交 manifest，最后持久化恢复
  检查点并删除所覆盖的 WAL 文件。SHM 段在 manifest 覆盖后按读者保护规则退役。
- 精确回执采用热内存加 SQLite 索引；回收热回执不破坏有效 epoch 内的重复写判断。
  已完整保留热索引时，新请求不额外查磁盘。新 epoch 的安全检查点会清理被 fence 的旧回执。
- 恢复以检查点为起点，只读取后续 WAL。即使检查点提交后尚未来得及 unlink 就退出，也不会
  重放整个已归档前缀；恢复后清理残留文件。序号包含零行 mutation，不靠行 offset 推断。
- 持久化积压受每表 Arrow 输入字节和存活段数量限制。可重试的持久化接纳背压不把表永久
  杀死；未知结果与持久性错误仍 fail-closed。重复检查点重试不会无限创建空 WAL。
- shutdown 关闭维护任务接纳、等待已接纳操作并有界 join 检查点线程，然后提交 WAL 尾部。
  退出不强制把最后尾部转成 Parquet；尾部由 WAL 恢复。
- WAL CRC32C 使用安全的 slicing-by-eight，保持原有校验值/文件格式，不引入 unsafe。

入口：`NativeStorageRuntime.start_native_ingest_with_config()`；配置包括
`NativeIngestConfig.with_checkpoint_interval()`、热回执预算和
`NativeAppendMaterializerConfig.with_max_buffered_bytes()` / `with_max_live_segments()`。
`NativeIngestHandle.checkpoint()` 可显式等到当前捕获前缀完成。
状态增加 `checkpoints_total` / `checkpoint_backpressure_total`。

## 实测

同一台机器、release 构建、本地 `/tmp` 所在 ext4。数字不是网络端到端延迟，也不是生产 SLA。

| 用例 | 结果 |
| --- | --- |
| 8192 键，初始化后 128 批 × 32 键更新 | 11.41 ms（含初始化；上一阶段约 28 ms，但输出语义已变） |
| CRC32C，256 MiB | 425.23 ms → 93.15 ms，约 4.6 倍 |
| 原生单列 append，983040 行、30 次持久化检查点 | 约 146.2 万行/秒；批次接纳 p99 370 μs，仅简化对照 |
| 原生 41 列盘口形状宽表，1 万标的，983040 行 | 校验优化前 35.48 万 → 40.92 万行/秒；批次接纳 p99 2844 → 2140 μs |
| 同宽表，500 次检查点、16384000 行 | 42.62 秒，38.45 万行/秒，接纳 p99 2477 μs，进程峰值 RSS 118248 KiB |

宽表为标的字符串和双边十档价格/数量共 40 个 int64 字段，预生成且可压缩，不是实际交易所
数据。每批 1024 行，每 32 批持久化一次；时间包含指纹、WAL、SHM、回执归档、Parquet、
manifest 和检查点，排除建表和测试数据生成。500 轮已跨过热回执淘汰点。

复现：

```bash
PYO3_PYTHON="$PWD/.venv/bin/python" cargo bench --offline -p zippy-engines \
  --bench key_value_materializer -- --sample-size 10 --measurement-time 2 --warm-up-time 1 --noplot

ZIPPY_CHECKPOINT_BENCH_ROUNDS=500 PYO3_PYTHON="$PWD/.venv/bin/python" \
  cargo test --offline --release -p zippy-server --test native_storage_runtime \
  native_checkpoint_throughput_benchmark -- --ignored --nocapture
```

## 验收与边界

最终门禁：`cargo test --offline --workspace`、全 targets/features 的 Clippy `-D warnings`、
`cargo fmt --check` 通过；Python 主包 605 passed / 1 skipped；轻量客户端 68 passed，
覆盖率 80.12%。两个 Python 包各自的 Black、Ruff、mypy 门禁均通过；新 `state.py` 已纳入
根包 mypy 检查（15 个文件），客户端检查 24 个文件。Maturin 已重建并验证导入，构建环境
仍提示缺少可选 `patchelf`，未影响本机测试。没有提交、推送或部署。

回归覆盖：1 条热回执/3 个内存段下多轮写入回收、原始 offset 精确重试、旧快照读取、
WAL 未检查点尾部恢复、零行写入、后台自动持久化、检查点先于 unlink 的恢复窗口、
错误锚点拒绝、回执事务冲突回滚；KeyValue 覆盖分片、重复版本、缺口、实例替换和预算。

这些结果验证了回收链路和本机合成负载下的改善，不等于真实全 A 股完整交易日验收。
尚需在目标机器用真实字段、峰值流量、多表/分片、慢消费者和磁盘故障做持续压测。
当前单表宽表吞吐未达到百万行/秒，不能据此承诺满足任意 Level2 峰值或微秒级交易延迟。
原始事件保序指接纳及持久化日志，不意味着旧 best-effort live 订阅自动具备完整重放或
exactly-once 交付；事件消费者仍须验证连续性，并使用持久化事件补缺口。

预算是每表未回收 Arrow 输入字节，不是整个进程 RSS 的硬上限。SHM 预分配、查询读者、
列索引和后台组件也占内存；多表部署须核算预算总和。Parquet 与当前 epoch 的磁盘回执
按数据量增长，需要容量规划；这次没有新增自动数据保留/压缩合并策略。
KeyValue 常驻状态仍随键数量增长，盘口场景应使用标的等有界键空间，而不是逐笔事件 ID。

`Persisted` 写入确认接口仍不支持；本轮没有把 `Memory` / `Wal` 的承诺偷偷提升成
`Persisted`。后台落盘可从检查点与表 manifest 验证。跨机器 KeyValue 快照 RPC、KeyValue
持久化和 delete 也未加入，具体消费迁移见 [迁移指南](key-value-v2-migration.md)。
