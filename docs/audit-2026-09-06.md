## 范围与结论

本次对运行时队列、source 生命周期、原生 ingest/WAL、流表与 KeyValue、响应式与截面
计算做了重点代码审查，同时检查 Python writer/subscriber、服务启动与停服、现有性能工具
和相关测试。仓库约 24 万行 Rust，包含测试；本报告不代表每一行均已人工审阅。
技术栈为 Rust、Arrow、DataFusion、Tokio、共享内存与 PyO3，Python 使用 uv 管理。

按 complexity-optimizer 的流程先测量再修改，保留输出顺序、空值、回滚、持久化确认与
订阅连续性检查。通用扫描器不支持 Rust，因此 Python/前端扫描结果只作线索，主要结论
来自 Rust 调用链审查、失败用例与本机基准。扫描排除了其他 `.worktrees` 和生成的前端资源。

已修复队列内存安全/唤醒风险、Hello 顺序竞态、Clip NaN panic、正常停服误报、段回收的
标识残留，并消除了多项重复扫描和复制。KeyValue 基准耗时下降约 62%；但原生写入的
累计容量限制仍阻碍全天 Level2 运行，不能据此宣称已完成全市场生产容量验收。

## 已落实的发现

令 N 为已知标的数，K 为本批更新的不同标的数，C 为列数，R 为已保留回执数，
ΔR 为新确认回执数，S 为保留段数，D 为本次回收段数。

| 优先级 | 位置 | 问题与修改 | 复杂度或资源变化 | 风险与验证 |
| --- | --- | --- | --- | --- |
| P0 | [spsc_data_queue.rs](../crates/zippy-core/src/spsc_data_queue.rs) | 公开的 `&self` 并发接口配合手写 `unsafe Sync`，没有强制 SPSC 所有权；多调用者可同时操作同一槽位。改用已有 crossbeam 有界数组通道，保留原 API。 | 常态仍为 O(1)，删除自定义 unsafe 存储、手工析构和冗余内部 Arc。 | 中：FIFO、容量、并发所有权、关闭后排空、源事件与全仓回归。 |
| P1 | 同上 | 原 `Condvar::wait` 与不持锁的 `notify` 存在丢失唤醒窗口；改为满载时选择等待可写事件或关闭通道断开。 | 热路径不再每次出队都调用 `notify_one`；关闭广播可唤醒全部等待者。 | 中：单/多写者关闭唤醒、非二次幂容量、多轮回绕。 |
| P1 | [core/runtime.rs](../crates/zippy-core/src/runtime.rs) | 控制队列空读后，Hello 和 Data 可先后到达不同队列；worker 取出 Data 时误判 Hello 缺失。取到首批数据后重新检查控制队列。 | 仅握手阶段增加一次控制检查；稳态处理不增加队列轮询。 | 中：原全仓测试实际失败；修复后 source runtime 21 项连续通过 50 轮。 |
| P1 | [native.rs](../crates/zippy-ingest/src/native.rs) `promote_wal_commit_locked` | 每次 WAL 确认重扫全部历史回执；改为用前次 durable sequence 限定新确认区间，重复/过期完成直接返回。 | O(R) → O(log R + ΔR)；逐批确认时累计平方级扫描变为 O(R log R)，每条回执只提升一次。 | 中：复用并扩展乱序 group commit 测试，确认未来的 Memory 回执不会提前变为 Wal。 |
| P1 | [latest_state.rs](../crates/zippy-engines/src/latest_state.rs) | 小批更新重建全市场 `slot → row` BTreeMap。改为连续行号数组，仅新增 key 时按有序 key 重建。 | 查询 O(N log N + K log N) → O(K)；新增 key 时重建 O(N)。 | 低：插入到排序前后、重复 key、既有 key 更新、空值和失败不变更状态。 |
| P1 | [reactive.rs](../crates/zippy-operators/src/reactive.rs)、[expression.rs](../crates/zippy-operators/src/expression.rs) | `min > max` 无法拒绝 NaN，`f64::clamp` 随后 panic。构造器拒绝 NaN；三条表达式路径共用 `clip_value`。 | O(1)；删除三处重复边界判断。 | 低：修复前回归测试复现 panic；覆盖上下界 NaN、直接/上下文/计划执行，保留无限边界。 |
| P1 | [server/runtime.rs](../crates/zippy-server/src/runtime.rs) `terminal_failure` | 正常关停后仍检查 Memory ingest/Flight 必须在线，使成功停服返回 UNAVAILABLE。将这两项检查限定在 admission 仍开放时。 | O(1)，生命周期判断与错误说明一致。 | 低：Python detached Gateway 用例复现；Rust daemon 测试扩展为 catalog-only/Gateway 两种模式，原生存储终止错误仍继续上报。 |
| P2 | [stream_table.rs](../crates/zippy-engines/src/stream_table.rs) `trim_published_retained_segments` | 回收段后未删除对应持久化标识；`Vec::remove(0)` 反复移动剩余描述符。回收时删除标识，两个 FIFO 改用 VecDeque。 | 队列搬移 O(D×S) → O(D)；标识删除另需 O(log S)，正常回收路径不再积累历史标识。 | 低：保留 persist 完成、reader pin 和外部 retention guard 前置条件，验证批量回收后的账本。 |
| P2 | [cross_sectional.rs](../crates/zippy-operators/src/cross_sectional.rs) | z-score/demean 复制已缓存的整个截面，又构造非空样本临时数组。先取得统计值再借用缓存，并直接扫描有效值。 | 仍为 O(N)，移除 O(N) 临时存储；保持原求和次序与总体方差定义。 | 低：现有排序、并列排名、null/NaN、零方差、上下文与直接计算一致性测试。 |

KeyValue 另删除了只写不读的 key 副本、sequence 与恒为 true 的 occupied 字段。
投影的槽位边界校验从每列每行一次，合并到整次投影入口；仍保留一次完整边界检查，
也避免 Utf8 预估长度时先索引、后检查的问题。

## 测试简化

- 将 9 个分片类型 smoke 测试合并为 1 个类型矩阵，覆盖 Date32、LargeUtf8、Int64、
  UInt64、Float64 与四种时间戳精度；由只验证长度，强化为两行批量路由与单值路由一致。
  稳定 hash 的 golden 用例及 null、NaN、顺序、错误回滚用例保留。
- 删除已被综合时序因子测试覆盖的独立 return warmup 用例。
- 删除读取 Rust 源码、断言必须包含 `UnsafeCell`/`AtomicUsize` 的实现形状测试，
  改用显式手动运行的性能基准；增加真实并发所有权与关闭行为验证。
- 复用已有 latest state、WAL group commit、daemon 生命周期测试补充边界，避免再复制
  一套 fixture。默认测试数减少，但新增 bug 和队列安全行为仍有覆盖。
- Python 客户端 67 项测试约 1–2 秒，覆盖率原为 80.03%。没有证据支持大量删除这些
  契约用例。测试多不等于冗余，读取源码字符串的断言、重复环境搭建更值得优先清理。

## 未关闭的容量与架构问题

1. **P0：原生 append 尚缺全天回收闭环。**
   [materializer.rs](../crates/zippy-ingest/src/materializer.rs) 的默认和硬上限均为 1024 个
   live segment，默认每段 65536 行，即满段情况下最多约 6711 万行，切换 epoch 产生部分段
   时更早耗尽。假设单表持续 50 万行/秒，约 134 秒达到这个行数上限；这是代码限额的算术
   推算，并非真实行情流量预测。当前 sink 持有历代 materializer，预检/发布遍历全部 live
   segments，没有将持久化水位推进、segment 释放、WAL checkpoint 与回执回收接起来。
   `NativeIngestConfig` 默认同一 epoch 保留 100 万回执，耗尽后拒绝新写入；按
   50 万行/秒、64 行/批推算约 128 秒。WAL 重启检查还有 16 GiB/100 万记录等累计限额。
   服务启动当前使用默认配置。应实施有界持久化与确认水位驱动的回收，并保留幂等重试
   下界、snapshot pin 和崩溃恢复一致性。直接提高限额只会延后问题。风险高，需独立设计
   与磁盘限速、恢复、长跑压测；本次未改变这些契约。

2. **P1：原生写入每批仍遍历历史段。**
   `preflight_live_segment_budget` 和 `build_publication` 都调用
   [append_live_segments](../crates/zippy-engines/src/stream_table.rs)，后者遍历 S 个段，
   包括 JSON 编解码和共享内存 attach。成本为每批 O(S)，并在表状态锁内执行。
   后续应让容量预检读取计数，发布复用带明确生命周期的 typed descriptor，并只为变更段
   构造增量；目标为预检 O(epoch 数)、发布 O(新增段数 + 活跃段)。风险中高，需验证 writer
   epoch、query pin 与发布版本，不能仅缓存无效期不明的描述符。

3. **P1：KeyValue 仍有完整快照成本。**
   `update_snapshot_storage` 每批调用 `build_snapshot_batch`，即使只更新一个 key，
   仍为 O(N×C)。本次只是把重复索引降为 O(K)，没有将整个 KeyValue API 变成 O(K)。
   下一步需要明确增量输出与完整快照消费者的接口，以 changelog 驱动高频订阅、按需生成
   稳定快照。风险高，验收必须覆盖旧快照不可变、下游输出契约和 reader 可见性。

4. **P1：rolling 因子的事务开销随窗口放大。**
   [reactive.rs](../crates/zippy-operators/src/reactive.rs) 的 `record_undo` 在一个事务中
   首次触及标的时 clone 整个历史窗口，窗口长度 W 时为 O(K×W)。可以改为追加/弹出操作
   日志和统计量快照，目标 O(本批行数)，但必须验证同标的多次更新、Skip、后续表达式失败
   和新标的回滚。另应专项核查 `E[x²] - E[x]²` 的大数小波动数值精度。

5. **P1：现有压测不能替代真实 Level2 验收。**
   segment-copy/forward 基准反复转发同一个 batch；设置 `symbols=10000`、batch=64
   并不意味着遍历了 1 万标的，实际该固定 batch 仅含 64 个。inproc 的首轮生成器也有
   相同缺陷，不能用其配置值证明实际覆盖规模。下一步需真实消息宽度、null 比例、逐笔/快照混合，
   1/32/64/1024 行批量、多表多订阅者、磁盘限速、开收盘突发、30 分钟以上长跑与恢复；
   报告 RSS、积压字节、fsync/rollover 尾延迟、p99.9 和序列连续性。
